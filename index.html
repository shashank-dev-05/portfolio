01 — How I build

Most internal tools fail because
nobody doing the work designed them.

I'm not a consultant parachuting into a process. I run the process, so I know which step people quietly skip and which part just looks inefficient on a flowchart. That's the whole advantage.

01

Sit in the problem

I do the job the tool is for. I know which field is always wrong and which report gets rebuilt by hand every Monday. You can't interview your way to that.

02

Reduce it to a system

States, rules, edge cases, who sees what. Before a line of code — what are the real outcomes, who can set them, and what happens when someone's on leave. Most of the work lives here.

03

Ship the thin version

Something real in the team's hands within days, not a spec deck in three weeks. Then I watch people use it wrong, which teaches me more than any requirements doc would have.

04

Harden it

Offline write-queues, role-based access, audit trails, fairness checks that can be defended to a manager. It runs in production with real compliance attached, or it doesn't count.

Quality review meant watching every verification call end to end and ticking a checklist by hand. I built a pipeline that does the tedious part: a Chrome extension pulls call and case data, a Flask backend transcribes it, and a three-tier engine scores it against the SOP. The reviewer still makes every final call — the system just stops them having to hunt for it.

8min → 30sper-call review time
18checkpoints scored per call
$0 / monthrunning cost, free tiers only
  • Three tiers in order of cost: fuzzy match on each agent's own speech patterns, then generic SOP patterns, then an LLM tiebreaker only for genuinely ambiguous cases
  • 14 SOP checkpoints plus 4 KYC cross-verification items per call
  • Hindi and Hinglish handling with custom dictionaries for Indian names, states, numerals and year variants
  • Tuned against real audit feedback across 8 agents and 350+ reviewed calls
  • Human-in-the-loop by design — the engine proposes, the reviewer decides

Shift and checker allocation was being done by hand, which meant it was also being done unevenly — and nobody could prove otherwise either way. I replaced it with an engine that assigns duty on transparent rules and shows its working, so every agent can see exactly why they got what they got. It ships as a module inside the V-CIP Portal.

05 — Where this scales

None of these are one-team problems.

I built each of these for the verification team because that's the team I sit in. But the underlying pattern isn't specific to verification — it's specific to how operations teams work. Here's where each one travels.

Built forMaker/checker verification
→
Applies toAny two-step review process

Case logging, role-scoped views, live stats and an audit trail. Any team where one person decides and another signs off has the same shape — onboarding, risk review, refunds, disputes, KYC re-verification.

Built forCall quality audits
→
Applies toAny SOP-scored interaction

The three-tier engine doesn't know it's auditing verification calls. Point it at a different SOP and it scores tickets, chats or emails the same way. The expensive LLM step only fires on genuine ambiguity, so cost stays near zero at scale.

Built forChecker allocation
→
Applies toAny rostered duty

Fairness scoring with a defensible audit view solves a people problem, not a verification problem. Every team that assigns duty by hand has the same trust gap — and the same manager fielding the same complaint.

Built forPOS reporting
→
Applies toAny report rebuilt by hand

Pulling live from Freshdesk and Sheets instead of exporting and pasting. If a team is rebuilding the same view every Monday, that's a connector and a dashboard, not a recurring four hours.

What I'd want to do with this

The pattern I keep hitting is that operations teams know exactly what's broken and have no route to fixing it in software. The gap isn't ideas or engineering capacity — it's that nobody sits in both places. I want to be the person who does: close enough to the floor to know which problem is real, technical enough to ship the fix, and disciplined enough to build it so it survives contact with compliance and scale.
